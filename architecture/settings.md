# Architecture: Settings/Ajustes hub (`features/settings/`)

Part of [ARCHITECTURE.md](../ARCHITECTURE.md)'s split — see that file for the index, and [CLAUDE.md](../CLAUDE.md) for project overview/commands/durable invariants. Covers `src/features/settings/menu_view.py` and the `metodos_pago_*`/`reglas_cobro_*`/`reset_*` file sets.

### `src/features/settings/menu_view.py` — `SettingsView` (the Ajustes hub)
A landing screen, not a table — back button + title + a small `QGridLayout` of section buttons ("💳 Métodos de pago", "📋 Reglas de cobro", "🗑️ Restablecer base de datos"), the same idea as `MainMenuWidget`'s top-level buttons but one level down. Each button calls a section's own `show_*_view(main_window)` helper. `show_settings_view(main_window)` is the module-level singleton-navigation function (identical pattern to `show_members_view`): caches one `SettingsView` as `main_window._settings_view`, adds it to `main_window._stack` once, `setCurrentWidget` thereafter. Wired from `MainMenuWidget`'s "⚙️ Ajustes" button (previously a no-op that only logged the click).

### `src/features/settings/metodos_pago_service.py` — `MetodosPagoService`
`is_fixed(nombre)` checks membership in `seed_db.METODOS_PAGO_FIJOS`. `list_metodos_pago()` returns every row (any `estado`) as plain dicts with a computed `"fijo"` bool. `add_metodo_pago(nombre)`/`rename_metodo_pago(id, nuevo_nombre)`/`set_metodo_pago_estado(id, estado)` all go through `get_session()` and call `record_log` (see `architecture/database.md`'s `audit.py` note) — `rename_metodo_pago` refuses and returns `False` if `is_fixed()` is true for the *current* name, without raising; `set_metodo_pago_estado` has no such restriction, so fixed methods can be deactivated (just never renamed or removed from the fixed set). **Decided (durable):** the 5 README-fixed methods can never be renamed or physically deleted, but can be deactivated like any custom method; custom methods (e.g. Bizum) are fully editable. **Decided (durable):** no method is ever a physical `DELETE` — "remove" always means `estado="inactivo"`, same pattern as `Socio` (nothing FKs into `metodos_pago` yet, so a hard-delete-with-in-use-guard wasn't needed; revisit once `Transaccion` rows can reference one).

### `src/features/settings/metodos_pago_dialog.py` — `MetodoPagoDialog`
One field (`nombre`). Same create/edit dual-mode shape as `MemberDialog`: pass `initial_nombre` for "rename" mode, omit for "new method" mode. `MetodosPagoToolBar` is responsible for never opening this in rename mode for a fixed method (see below) — the dialog itself doesn't know about the fixed set.

### `src/features/settings/metodos_pago_toolbar.py` — `MetodosPagoToolBar`
Nuevo/Editar/Activar/Desactivar/Refrescar, same `QToolBar` shape as `MembersToolBar`. `on_edit_metodo` checks `service.is_fixed(nombre_actual)` before opening `MetodoPagoDialog` and shows a `QMessageBox.information` instead if true; like `MembersToolBar.on_edit_member`, it refuses (info message, no dialog) when more than one row is selected. **Decided (durable, PLAN.md 1):** "Activar" and "Desactivar" are two separate, always-batch-capable buttons (`on_activate_metodos`/`on_deactivate_metodos`, both routed through the shared `_set_estado_for_selection(nuevo_estado)`) rather than a single ambiguous toggle — each acts on every selected row, skipping (no-op) any row already in the target `estado`, and asks one `QMessageBox.question` for the whole batch only when deactivating (mirroring `MembersToolBar._confirm_deactivation`'s singular/plural phrasing), never when activating.

### `src/features/settings/metodos_pago_view.py` — `MetodosPagoView`
The actual table screen (ID/Nombre/Estado/Tipo columns, `"Tipo"` = `"Fijo"`/`"Personalizado"` computed from `is_fixed`). Small-grid shape, no search/sort composition (unlike `MembersMenuView`) — per `UI_PROPOSAL.md`'s guidance that `metodos_pago`/`reglas_cobro` are low-row-count config grids, not full data screens. Its back button (`on_back_to_settings`) returns to the Settings hub (`main_window._settings_view`), **not** the main menu — it's nested one level under Ajustes. `show_metodos_pago_view(main_window)` is the same singleton-navigation pattern, cached as `main_window._metodos_pago_view`.

### `src/features/settings/reglas_cobro_service.py` — `ReglasCobroService`
Same shape as `MetodosPagoService` but simpler: no fixed set at all (**decided, durable:** the club can define multiple named billing rules — `descripcion` doubles as the name, e.g. "Cuota general" vs. "Cuota reducida" — every field on every rule stays fully editable). `list_reglas_cobro()`/`get_regla_cobro(id)`/`add_regla_cobro(data)`/`update_regla_cobro(id, data)` (full-form update, diffs changed fields into the audit log like `MembersService.update_member`)/`set_regla_cobro_estado(id, estado)`. **Decided, durable:** same soft-deactivation-only pattern as `MetodoPago` — "remove" is `estado="inactivo"`, never a physical `DELETE`.

### `src/features/settings/reglas_cobro_dialog.py` — `ReglaCobroDialog`
Five fields: `descripcion*`, `cuota_mensual`/`penalizacion`/`descuento` (currency, `QDoubleValidator` pinned to the `QLocale.c()` — i.e. `.`-decimal — locale so parsing doesn't depend on the OS locale), `plazo_pago` (days, `QIntValidator`). `get_data()` returns `decimal.Decimal`/`int`/`None` values ready for `ReglaCobro(**data)`. Same create/edit dual-mode shape (`initial_data`) as `MemberDialog`/`MetodoPagoDialog`.

### `src/features/settings/reglas_cobro_toolbar.py` — `ReglasCobroToolBar`
Nueva/Editar/Activar/Desactivar/Refrescar. Unlike `MetodosPagoToolBar`, `on_edit_regla` has no fixed-method-style guard — every rule is always editable — but it shares the same single-row-only restriction (info message, no dialog, if more than one row is selected). "Activar"/"Desactivar" (`on_activate_reglas`/`on_deactivate_reglas`) follow the identical always-batch-capable, no-op-on-already-in-target-state, confirm-only-when-deactivating shape as `MetodosPagoToolBar`'s.

### `src/features/settings/reglas_cobro_view.py` — `ReglasCobroView`
Same small-grid shape as `MetodosPagoView` (ID/Descripción/Cuota mensual/Plazo (días)/Penalización/Descuento/Estado columns), same back-to-hub navigation, same `show_reglas_cobro_view(main_window)` singleton pattern (cached as `main_window._reglas_cobro_view`).

### `src/features/settings/reset_service.py` — `ResetService`
`full_reset()`: `Base.metadata.drop_all(bind=engine)` + `create_all(bind=engine)` (imports `engine` from `database.session` *inside* the method — see the "Gotcha" callout in `architecture/database.md`'s `session.py` section), then `seed_db.seed_all()`, then one `record_log` call into the now-empty `logs` table documenting the reset itself (`accion="reset_completo"`). Never touches `data/club_manager.db` as a file (no `os.remove`) — sidesteps Windows file-locking/WAL concerns entirely. `scoped_reset()`: row-deletes `Transaccion`/`SaldoSocios`/`Periodo` inside one `get_session()` block (leaving `Socio`/`MetodoPago`/`ReglaCobro`/existing `Log` rows untouched) and records an `accion="reset_parcial"` log the normal way. **Decided, durable (PLAN.md 2.15):** both a full wipe and a scoped reset are supported — full wipe is "start over," scoped reset is "discard this season's financial activity but keep membership/config."

### `src/features/settings/reset_view.py` — `ResetView`
No table — two `QGroupBox` panels, one per operation, each gated by its own type-to-confirm `QLineEdit` (button starts `setEnabled(False)`, a `textChanged` handler enables it only on an *exact* string match) plus a final `QMessageBox.question` before the service call fires. **Decided, durable (PLAN.md 2.15, explicitly requested as "very safe"):** never a single dismissable dialog. The two operations use deliberately different confirmation phrases (`"REINICIAR"` for scoped, `"BORRAR TODO"` for full) and different button colors (amber `#B8862B` vs. danger red `#A1382F`, inline `setStyleSheet` rather than the shared QSS) specifically so they can't be mis-clicked for each other. Both text fields clear themselves (re-disabling their button) after a reset attempt, successful or not. `show_reset_view(main_window)` is the same singleton pattern, cached as `main_window._reset_view`.
